# القمة في القسم اللفظي — بوابة نماذج القسم اللفظي

موقع ثابت بالكامل يجمع **301 نموذجًا** لتدريب **القسم اللفظي** من اختبار القدرات العامة،
إعداد الأستاذ **عبد الرحمن سيد منصور** — مدرب القدرات وماجستير اللغة العربية.
بحث عربي فوري بالاسم أو بالرقم، ومتابعة تقدّم محفوظة على جهاز الطالب.

**لا يوجد خادم، ولا قاعدة بيانات، ولا خطوة بناء مطلوبة للنشر.** الملفات المرفوعة هي الموقع نفسه.

---

## Quick start

```bash
npm start           # preview at http://127.0.0.1:4173 (PORT=5188 npm start to change)
npm run verify      # rebuild data + run every test + check the lock + validate offline
npm run build:lock -- --student "…" --admin "…"   # re-seal the links (see "The lock")
```

Nothing to install — every script is plain Node (>= 18) with zero dependencies.
Only the three Python tools need Python, and only when a source document or an image
changes; their outputs are committed.

### Why no framework

The site is one screen over 301 records. Vanilla ES modules ship well under 30 KB of
JavaScript; React plus a bundler would have cost roughly ten times that, plus a build
step that can break a deployment. Everything loads as plain static files with
**relative** paths, so the site works identically at `user.github.io/repo/`, at
`user.github.io/` and on a custom domain.

## Updating the exam list

1. Drop the new export into `data/source/forms.json` (replacing the old one).
   The original file is never modified by any script — and it is **not in git**, because it
   holds the form links in the clear. Keep a backup of it somewhere else.
2. Run `npm run build:data`. This writes the public dataset (no links) and
   `data/source/links.generated.json` (the links, secret).
3. Run `npm run build:lock -- --student "<current>" --admin "<current>"` to re-seal the
   links into `assets/data/unlock.json`. The current passwords are in the console
   (`lock-admin.html`) if you have forgotten them.
4. Run `npm run verify`, then commit `assets/data/exams.json`, `assets/data/unlock.json`,
   `llms.txt`, `sitemap.xml` and `data/build-report.json`. CI does not rebuild — it cannot,
   the source is not there — it checks what you committed.

`build-data.mjs` validates every record and prints what it published and what it
excluded. A record with a missing title, a non-https URL, a duplicate number or a
duplicate link is **left out of the site entirely** rather than rendered as a broken
exam. `data/build-report.json` lists any exclusions.

The source schema currently in use (Arabic keys, exactly as exported):

```json
{
  "المشروع": "…", "المعلّم": "…", "الجوال": "…", "الشعار": "…",
  "عدد_النماذج": 301, "كلمة_المرور": "…", "تاريخ_الإصدار": "YYYY-MM-DD",
  "إجمالي_الأسئلة": 3657,
  "النماذج": [{ "القسم": 1, "الموضوع": "…", "اسم_النموذج": "…",
                "عدد_الأسئلة": 13, "الرابط_المختصر": "https://forms.gle/…",
                "رابط_النموذج": "https://docs.google.com/forms/d/e/…/viewform" }]
}
```

`build-data.mjs` tolerates a bare array of forms too, and keeps any valid https URL
even when it is not a Google Forms link.

**The question count is per record, not per site.** These forms run from 5 to 16
questions, so every card states its own count and there is a "الأقصر أولًا" sort. If a
future export drops `عدد_الأسئلة`, that card simply omits the line.

### «زبدة الأقسام» — derived, not asserted

The shortlist is a checkable claim, so it is computed rather than typed in. Its name is
the teacher's: «زبدة الأقسام» since 2026-09-24 (it was «الأكثر تكرارًا» before). The name
is `label` in `data/source/priority.json` — the site, the about page's section and the
console all read it from there through `assets/data/shortlist.json`, so a rename is that
one line and `npm run build:data`, plus the default in `derive-priority.py`.
`tools/derive-priority.py` produces `data/source/priority.json`; **134 sections** are
flagged in the current build.

**Where the claim comes from.** Not from either teacher's opinion: from a separate
reference compilation that collects the passages that recur most in the real exam.
**It is never named** — not on the site, not in `llms.txt`, not in the data or in this
repository, which is published with the site. The teacher asked for that (2026-09-24), and
`tools/test-seo.mjs` fails if the name comes back anywhere in the tree. This site and الأستاذ أحمد طلعت's site index
the *same* 301-section compilation — 300 of the 301 topics are identical, the odd one out
being a spelling variant of المدرسة المونتيسورية — so "which of the 301 recur most" is a
property of the content, and the answer is the same for both sites.

**How the match is made.** Not on section titles. The two compilations pair their passages
differently — the reference compilation joins passages that the 301 file keeps in separate
sections — so titles disagree even where the content is identical. Matching on titles
produced obvious nonsense («العصافير» → «الدعاء» at 0.57 similarity).

The questions themselves are the stable unit. So the script fingerprints every six-word
window of each section's text, discards windows that appear in more than two of the 301
sections (boilerplate such as «اختر المفردة الشاذة»), and asks which of the 301 sections
the reference text came from.

The evidence comes out cleanly bimodal, which is what a real correspondence looks like and
a coincidence does not:

| share of a reference section's distinctive text found in a 301 section | sections |
| --- | --- |
| 0.9 – 1.0 | **125** |
| 0.1 – 0.8 | 17 |
| none at all | 159 |

The cut (`MIN_SHARE = 0.30`, `MIN_WINDOWS = 20`) sits in the empty middle, so it is not
delicate. The script refuses to write a list far from the size of the reference compilation.

```bash
python tools/derive-priority.py            # report only
python tools/derive-priority.py --write    # update priority.json
npm run build:data                         # then rebuild
```

The two source `.docx` files are **not in this repository**. `QIMMA_SOURCES` (or `BASE` in
the script) points at the folder holding the 301 compilation; `QIMMA_PRIORITY_DOCX` must
point at the reference compilation itself, and has no default, because its file name would
name it. The derived list is committed, so the script only needs to run when one of those
documents changes.

**How this differs from the list on الأستاذ أحمد's site.** His ships 140 sections; the two
agree on 126.

- **8 sections he lists have no shared text at all** with the reference compilation —
  23, 49, 96, 116, 117, 143, 167, 260 — so nothing here supports flagging them.
- **8 sections with overwhelming support are missing from his list** — 24, 50, 62, 130,
  144, 158, 197, 261 — several at a 0.97–1.00 share over hundreds of windows.
- His 122–254 band is the weak one: 6 listed, 1 supported. His 1–121 band is 91% supported
  and his 255–301 band 97%.

That is why this site ships the derived list rather than a copy of his.

**Overriding it by hand.** If the teacher wants a different set, write the numbers straight
into `sections` and run `npm run build:data`. Nothing enforces the derivation — but note
the reason in `_note`, because the next person to run the script with `--write` will
otherwise overwrite the edit.

**Hidden unless the teacher shows it.** The shortlist ships switched off, and switching it
is the teacher's call, made from `lock-admin.html` («زبدة الأقسام» → أظهرها /
أخفِها). With it off, a visitor gets a site that never had it: no hero figure, no
quick-access tile, no toolbar toggle, no card pill, no second progress track, no sort
option, no section or FAQ entry on the about page, no line in `llms.txt`.

That is done by keeping every trace of it out of what ships by default, not by hiding it:

- `assets/data/exams.json` carries no `p` flag and no `meta.priority`. The list and all of
  its copy — label, blurb, the about page's section — are in `assets/data/shortlist.json`,
  written by `build-data.mjs`.
- `assets/data/features.json` is the switch: `{ "shortlist": false }`. Only the console
  writes it — one commit through the same GitHub token the password change uses, after
  which it waits for the live site to serve the new value.
- `assets/js/shortlist.js` reads the switch at boot and fetches the list only when it is on.
  Anything unreadable counts as off. `app.js` then flags the cards and builds the hero
  figure and the sort option; the about page fills an empty `<template>` marker.
- The markup keeps the toggle, the tile and the progress track hidden and wordless.
  `tools/test-seo.mjs` fails if a page or `llms.txt` carries a word of the feature, and
  `tools/check-links.mjs` fails if `exams.json` does, or if the switch is not `true`/`false`.

CI accepts either state, since the console's commit is what triggers it. An empty
`sections`, or no `priority.json`, removes `shortlist.json`; the switch then has nothing to
show, and the console says so and will not offer to.

This hides the feature from visitors, not the list from someone reading the repository:
`shortlist.json` is committed and served (nothing links to it while the switch is off), and
the repository is public. Keeping the list itself private means a private repository.

The build reports `priority.flagged` (how many the list holds) and `priority.unknown` (numbers on
the list that no published form answers to — dropped rather than failing the build, and
printed during the build so a typo is visible immediately).

## The running order — why the export's numbers are not the site's

`data/source/forms.json` numbers its sections in the order the forms were built:
the compilation that ran to **262** sections, plus **39** added after it. The teacher
has since re-ordered the compilation his students read from — **the last twenty of
the 262 moved to the front**, and everything before them moved down by twenty — and
the site has to show his numbers, not the export's.

The export is never edited, because it is the only thing that ties a section to its
Google Form. So the new order lives beside it, in `data/source/section-order.json`,
and `build-data.mjs` applies it while it builds the dataset:

```
export 243..262  ->  1..20      the twenty that moved to the front
export   1..242  ->  21..262    everything before them
export 263..301  ->  263..301   the 39 added later, untouched
```

**One rule follows from this, and everything in `data/source/` obeys it:** a file in
`data/source/` is written in the **export's** numbering. `priority.json` is, and
`build-data.mjs` translates it on the way out. That keeps `derive-priority.py` correct
without it knowing that a re-ordering ever happened — and it is why the shortlist still flags the same
**passages** it did before, at their new numbers.

`tools/build-order.py` does not take the rule above on trust. It reads the document's
own index, applies the rule, and then checks all 301 pairs **by name** against the
export. It refuses to write unless every one of them agrees, so the file can be
regenerated safely whenever the document changes:

```bash
python tools/build-order.py            # report only
python tools/build-order.py --write    # update section-order.json
npm run build:data                     # then rebuild
```

Two kinds of name are tidied before the comparison, both agreed with the teacher: a
conjunction typed as a separate word (`مالك و الحياة` -> `مالك والحياة`), and one
spelling of Montessori. Everything else is the document's wording, character for
character.

The document is his working file and is **not** in this repository; set
`QIMMA_ORDER_DOCX` to it, or edit `DOCX` in the script. The derived file is committed,
so the build never needs it.

**Progress already on a student's device** is stored against section numbers, so it
would point at the wrong passages after a change like this. `assets/js/store.js` moves
it once, on read, and stamps it with schema 2 — including a file exported from another
device before the change. `tools/test-store.mjs` covers both paths.

**The Google Forms keep their own titles.** A form is still named for the number it had
when it was built (`القسم الثالث والأربعون بعد المئتين — خلق المؤمن والحقد` is now section
1 here), and the teacher is renaming them himself. Nothing on the site refers to a form's
internal number.

## One numbering

The sections carry one number each — the one they have today — and the site never says
what a section used to be numbered: no «كان القسم N» on a card, no old number answered by
the search, no explanation on the about page, nothing in `llms.txt`. That was the
teacher's decision (September 2026): the numbering is settled, and a second one only
confuses. The comparison table, the map extracted from it and `build-map.py` were removed
with it; they are in the first commit if they are ever needed again.

`tools/check-links.mjs` and `tools/test-search.mjs` fail if a record carries an old
number (`o`) or `meta` carries a map, and `tools/test-seo.mjs` fails if a page, a page
script or `llms.txt` mentions an old numbering. Moving a student's stored progress to the
current numbers (`store.js`, above) is unaffected: it is silent and says nothing.

## Deploying to GitHub Pages

### The automatic path (recommended)

1. Push this folder to a GitHub repository.
2. **Settings → Pages → Build and deployment → Source: GitHub Actions.**
   Do this *before* the first run — see the troubleshooting note below.
3. Push to `main`. `.github/workflows/deploy.yml` runs the tests, checks the lock,
   validates the committed dataset, **stamps the real Pages URL** into the canonical/OG/
   sitemap/robots tags, adds `.nojekyll`, and deploys. It does **not** rebuild the dataset:
   the source export is not in the repository (see "The lock").

`actions/configure-pages` reports the real URL, so the same workflow is correct for a
project page, a user page or a custom domain.

#### If the build fails at "Configure Pages"

```
Error: Get Pages site failed. Please verify that the repository has Pages
enabled and configured to build using GitHub Actions.
```

Pages has never been turned on for the repository, so there is no Pages site to look up.
It is a repository setting, not a problem with the site.

**Fix:** *Settings → Pages → Build and deployment → Source: **GitHub Actions***, then
re-run the workflow. The workflow already tries to avoid this (`enablement: true`, which
needs *Settings → Actions → General → Workflow permissions* set to **Read and write**),
and the step is `continue-on-error` with a URL fallback — but the final `deploy-pages`
step still requires the one-time setting.

### The manual path (deploy from a branch)

Run this once first, so the absolute URLs in the metadata are correct:

```bash
npm run set-url -- https://your-name.github.io/your-repo/
```

Then set **Settings → Pages → Source: Deploy from a branch**. `.nojekyll` is already
committed, which matters here: without it Jekyll drops files and chokes on the Arabic
filenames under `data/source/`.

`npm run set-url -- --reset` puts the `__SITE_URL__` placeholders back.

## Design system

Tokens live in `assets/css/tokens.css`. The palette was sampled directly from the brand
seal, which carries only two colours:

| Role | Light | Dark |
| --- | --- | --- |
| Royal navy (structure, text) | `#0e214e` | `#eaf0fb` on `#071539` |
| Gold (**the** action colour) | `#c9a86b` fill, navy ink | `#dcbb85` fill, navy ink |
| Gold as text | `#7a5417` | `#e2c48d` |
| Paper | `#f6f3ec` / `#ffffff` | `#071539` / `#0f2150` |

Rules the implementation follows:

- **Gold is the only action colour.** The seal has no third colour, so gold does the work
  a burgundy would do in a three-colour brand: a muted fill with navy ink on it. On the
  exam cards, where «ابدأ الاختبار» repeats 301 times, the button is a gold *tint* that
  fills solid on hover, so the grid stays calm.
- **Gold as a fill and gold as text are different tokens.** `--accent` is light enough to
  put navy on; it is never used for text. Text uses `--gold-ink`.
- **A control's edge is not a card's edge.** `--control-border` meets the 3:1 that WCAG
  1.4.11 asks of a control boundary; `--border-strong` is decorative and much lighter.
- **Minimum body size is 15px, minimum metadata size is 13px.** Nothing smaller.
- **Every text colour meets WCAG AA (4.5:1)** against its own background, in both themes —
  and `tools/test-tokens.mjs` re-measures all 23 declared pairs on every `npm test`,
  compositing translucent washes over their real backdrop first.
- **Light is the default for every visitor**, whatever their operating system says. Dark
  is opt-in only, through the header toggle, and the choice is remembered.
- **The seal always sits on a white disc** so it reads identically in both themes; only
  the rim, ring and shadow around it adapt.
- **«القمة» is drawn, not illustrated.** The peak behind the hero is a CSS `clip-path`,
  not an image: it costs nothing, scales to any viewport and recolours with the theme.

## Behaviour worth knowing

**Search** (`assets/js/search.js`) folds alef/hamza variants, ة, ى, ؤ, ئ, diacritics and
tatweel, and both Arabic-Indic and Latin digits. The definite article and a leading «و»
are indexed as extra stems, so «زلازل» finds «الزلازل والسكري». A pure number addresses a
section directly — **and also matches the number that section used to carry**, ranked below
the current one and labelled in the result line. If a strict pass finds nothing, a second
pass tolerates a one-character typo. Matches are highlighted on the original Arabic title
through an index map, so folded characters still highlight correctly.

The normaliser is duplicated in `tools/build-data.mjs` (which builds the keys) and
`assets/js/search.js` (which matches them). **`tools/test-search.mjs` fails if the two ever
disagree**, on ten samples and on all 301 stored keys.

**State lives in the URL.** `?q=…&range=…&status=…&sort=…&key=1` — any view can be shared,
and the back button works. `#exam-47` deep-links to a section, loading more batches if
needed.

**Progress is device-local.** «مُنجز», «المفضلة» and «آخر ما فتحت» live in `localStorage`
only. Nothing is ever sent anywhere. Every storage call is wrapped, so a private window or
blocked site data keeps working in memory instead of throwing. Stored data is sanitised on
read, writes are debounced and flushed when the tab is hidden, and a second open tab picks
up changes through the `storage` event instead of overwriting them.

**Progress can move between devices.** Because it is local, a new phone starts empty — so
the progress panel has «حفظ نسخة» and «استعادة نسخة». The export is a small JSON file the
student keeps; the import merges by default, so restoring on a phone that has already been
used does not wipe it. This is the only transfer the site has: no account, no server.

**How "done" gets recorded.** Opening a form *is* doing it: any link that opens one marks
it done immediately, with an «تراجع» undo in the toast. The round checkbox on each card
toggles the mark by hand at any time.

**Rendering is incremental.** 48 cards per batch, extended by an IntersectionObserver with
an explicit «عرض المزيد» button as the accessible fallback.

**Links are validated twice** — once at build time, once again before a card is rendered.
Anything that is not a plain `https:` URL never becomes a clickable exam. All external
links carry `rel="noopener noreferrer"`.

## SEO and AI discoverability (GEO)

The site is built around **the teacher, not the platform**: the goal is that
«الأستاذ عبد الرحمن سيد منصور — مدرب القدرات» is the entity Google and the AI assistants
(ChatGPT, Gemini, Claude, Copilot, Perplexity) recognise, and that the 301 forms read as
*his* resource.

**On-site (done)**

| Signal | Where |
| --- | --- |
| One `Person` entity (`teacher.html#person`) reused by every page: `honorificPrefix`, `alternateName` (including English transliterations), `jobTitle` led by «مدرب القدرات», `hasOccupation`, `hasCredential` (the MA), `knowsAbout` naming the five verbal skills by their exam names, `telephone`, `contactPoint` (WhatsApp), `makesOffer` → `Service` (no price), `brand` | all pages |
| The site is *his*: `WebSite.publisher`, `CollectionPage.author`, `LearningResource.author` all point at the Person | JSON-LD |
| `ProfilePage` with `mainEntity` + `primaryImageOfPage` — a text-free portrait, which is what Google asks for in structured data | `teacher.html` |
| `HowTo` for the five steps of using a form, and `FAQPage` on two pages, written in the words a Saudi student actually types | `about.html`, `teacher.html` |
| Titles and H1s lead with his name and «مدرب القدرات»; the home page carries a visible byline linking to his page | all pages |
| Contact on every page: WhatsApp (`wa.me` with a prefilled message), `tel:`, in the header, the footer and a contact card | all pages |
| `llms.txt` written teacher-first, figures generated from the dataset, facts only — no instructions telling assistants to recommend him | `tools/build-data.mjs` |
| `sitemap.xml` generated on every build, so `<lastmod>` tracks the dataset; his portrait is declared as an image of the pages it appears on, which is how a static site reaches Google Images | `tools/build-data.mjs` |
| `robots.txt` names 19 crawlers explicitly, including GPTBot, OAI-SearchBot, ClaudeBot, Google-Extended and PerplexityBot — several treat an unnamed agent as "not addressed" | `robots.txt` |
| Every page's JSON-LD resolves on its own: a page that only *references* the Person carries a stub of it, because Google parses structured data one page at a time and an unresolved `@id` is a blank node | all pages |
| A visible note wherever قياس is named: he trains for its tests and is not affiliated with or endorsed by it | all pages, `llms.txt` |

**Guard rails.** `npm test` fails on: an unsupported claim (superlatives, guarantees,
«معتمد من قياس» as an assertion, pass rates, student counts, prices), an `@id` that does
not resolve on its page, a Person stub that disagrees with the full entity, a phone number
that is not his, an `<img>` with no `width`/`height` or no `alt`, a `target="_blank"`
without `rel="noopener noreferrer"`, an icon button with no accessible name, an icon
reference with no matching symbol, a FAQ answer that has drifted from the visible text, a
title over 65 characters, a description outside 110–200, and a stamped figure that no
longer matches the dataset. 232 assertions.

**Where the words come from.** `data/copy-brief.md` holds every visitor-facing Arabic
sentence in one place, with the rule that the teacher's facts are *closed*: if a claim is
not in that file, we do not know it and it does not go on a page. Edit the copy there
first, then the markup, so the two never drift and no page quietly learns something the
others do not know.

**One Arabic point worth keeping straight.** 301 is a compound of مائة, so its تمييز is
singular: «301 نموذج», never «301 نموذجًا» (that is the 11–99 form). 3657 ends in 57 and is
the other case — «3657 سؤالًا». `unitNoun()` in `tools/build-data.mjs` gets both right from
`Intl.PluralRules('ar')`, so generated text must go through it rather than hard-coding a
word.

**What only the owner can do**, in priority order:

1. **Google Search Console** — verify, submit `sitemap.xml`, request indexing of
   `/teacher.html`.
2. **Bing Webmaster Tools** — import from Search Console and enable IndexNow. Bing's index
   feeds ChatGPT search and Copilot, so this is an AI-visibility step, not just a Bing one.
3. **Make the name consistent everywhere** — WhatsApp Business profile, and any social
   account he opens: the same «الأستاذ عبد الرحمن سيد منصور – مدرب القدرات», the same phone
   format, each linking back to this site. **He supplied no social accounts, so `sameAs` is
   deliberately absent** rather than guessed; add the real URLs to the `Person` node in
   `teacher.html` when he has them.
4. **Mentions from other sites** — anything covering his courses or workshops. Web mentions
   correlate with AI visibility more strongly than backlinks alone.
5. **A YouTube channel** with short verbal-section explanations, titled with his name, then
   added to `sameAs`.
6. **A custom domain** (`.sa` or `.com`) — a stronger country and brand signal than a
   `github.io` path.

Not worth doing: Wikidata/Wikipedia entries for a non-notable person, FAQ markup for rich
results (Google removed them in May 2026 — ours is for people and AI readers), or Course
rich results (retired in June 2025).

## The lock — how the form links are protected

This site has no server, so it cannot keep a secret by hiding it: whatever the page can
read, the reader can read too. A password that only greyed out the buttons would leave
all 301 Google Forms links sitting in `assets/data/exams.json` for anyone who opened the
network tab. So the links are not hidden. They are **encrypted**, and the password is the
key.

```
assets/data/exams.json      numbers, titles, question counts — and NO links
assets/data/unlock.json     the links, AES-256-GCM under a key derived from the student
                            password (PBKDF2-SHA-256, 600,000 rounds), plus a "keyring":
                            the student password sealed under the ADMIN password
data/source/forms.json      the plain links — gitignored, never published, keep a backup
```

Until a password decrypts `unlock.json` there is no link anywhere in the page. A locked
card's button is a real `<button>`, not a link with its `href` removed; it sends the reader
to the gate, because that is the only thing it can do. A wrong password does not "fail a
check" — AES-GCM's authentication tag refuses to decrypt, and there is no separate password
hash in the file to attack instead.

One implementation, three callers: `assets/js/lock-crypto.js` is imported unchanged by the
site (`lock.js`), by the console (`lock-admin.js`) and by the build (`tools/build-lock.mjs`).
A lock whose writer and reader are two implementations will one day disagree with itself.

### What a student sees

The list is open — numbers, titles and question counts are what students search for and
what Google indexes. Only the door to the form is shut. The password is typed once and
kept on the device; on every visit the site re-fetches `unlock.json` (with `cache:
'no-store'` **and** a one-shot query string, and this site registers no service worker) and
compares its version with the one the device unlocked. A new version means the teacher
published a new password: the saved one is dropped, the gate says «تم تغيير كلمة المرور»,
and nobody has to clear anything. Progress and favourites are untouched by all of this.

Arabic-Indic digits, bidi marks and stray spaces are normalised on both sides, so a
password typed on an Arabic keyboard opens a file sealed from a Latin one.

### Changing the password — the teacher's path

`lock-admin.html` is not linked from anywhere, is `noindex`, and holds nothing: it decrypts
the keyring in the browser with the admin password and never stores or sends it.

1. Open `lock-admin.html`, enter the **admin** password.
2. The console shows the **current** student password (to resend on WhatsApp) and the
   version that is live.
3. Type a new student password twice — «اقترح كلمة قوية» generates a good one — and press
   «جهّز الملف الجديد». The console re-seals all 301 links and proves the result opens
   before it offers it.
4. Press **«انشر على الموقع الآن»**. The first time, it asks for a GitHub fine-grained token
   (Contents: Read and write, this repository only), pasted once and kept in the teacher's
   browser. From then on it is one click: the console commits `assets/data/unlock.json`
   through the GitHub API, Pages redeploys, and the console watches the live file until it
   is serving the new version — usually a minute or two. No file is ever opened by hand.

   Fallback, under «إعدادات متقدمة»: download the file and drop it over `assets/data/` on
   GitHub. The repository and branch are auto-detected from the site's address; a custom
   domain needs them typed once.

The admin password can be changed from the same page. There is no recovery for a lost admin
password other than rebuilding the file from the source with `build-lock.mjs`.

### What this protects against, and what it does not

- **Anyone without the password:** protected. No served byte contains a link, and
  `tools/test-lock.mjs` searches every published file for the *shape* of a Google Forms
  link (with positive and negative controls) so a leak cannot ship.
- **A student sharing the password:** not protected, and nothing static could be.
  Rotation is the remedy, and rotation is one click.
- **An offline guess against `unlock.json`:** the file is public, so the password is the
  whole defence. Order of magnitude on one high-end GPU against 600,000 PBKDF2 rounds:
  four digits fall in seconds, seven digits in minutes, eight characters from the
  suggester's 31-letter alphabet in centuries. **Use the suggester.** The console's meter
  says which of the three a password is, and flags the one string it must never be —
  the teacher's phone number is printed on every page.

There is deliberately no lockout after N wrong tries in the UI: a counter in the reader's
own browser slows nobody who has opened the console, where the real cost is the key
derivation per guess. A lockout would only punish a student who mistyped.

### Recovery

`data/source/forms.json` is the only plain copy of the links on disk, and it is not in git.
If it is lost, the console's «نسخة احتياطية من روابط النماذج» exports the links back out of
the encrypted file (admin password required). Keep that export off GitHub.

### Commands

```bash
npm run build:data                                     # dataset (no links) + links.generated.json
npm run build:lock -- --student "…" --admin "…"        # seal; refuses to write a file it cannot open
node tools/build-lock.mjs --verify                     # shape + coverage (npm run verify runs this)
QIMMA_STUDENT_PW='…' node tools/check-links.mjs        # open the seal and validate every URL
QIMMA_STUDENT_PW='…' QIMMA_ADMIN_PW='…' node tools/build-lock.mjs --verify   # both seals open
```

`tools/test-search.mjs` fails the build if a record in `exams.json` carries a link field,
and `tools/test-lock.mjs` fails it if the shape of a form link appears in any published
file, if the seal does not cover every section, or if the plain sources are not gitignored.

  maskable icons (inset to survive Android's circular crop).
